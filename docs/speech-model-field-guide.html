What each thing is

Voice agent vs ASR vs TTS, and streamed file output vs continuous audio — the distinctions that decide which model fits a workload.

Voice Agent

A voice agent (gpt-live-1) holds a spoken conversation — it listens while it speaks (full duplex) and delegates reasoning/tools to a backend. It is not a transcriber.

Asr

ASR / transcription turns speech into text. Diarization additionally labels WHO spoke. Some endpoints do neither speaker labeling (e.g. gpt-live-transcribe).

Tts

TTS turns text into spoken audio (e.g. gpt-4o-mini-tts). The reverse direction of ASR.

Streamed Vs Continuous

Streamed file / committed-turn output processes a bounded chunk and RESETS speaker labels each request. Continuous audio (classic ConversationTranscriber) keeps one session and carries speaker identity across the stream — which is why it showed the best continuity here.

Realtime Prompted

The six GPT-Realtime models are conversational models PROMPTED to emit Speaker A/B text. That is generated labeling, not native diarization.

Aliases

rtt (openai 10s chunks), rttold (classic continuous), rttheb (Azure LLM Speech). Tested paths vs unverified paths are marked per card.

Methodology & caveats

  • fixture: Same source test.mp3 seconds 300–330 (30s), decoded once to mono PCM16 24kHz.
  • commits: Two 15-second commits in ONE retained conversational session.
  • pacing: Audio paced at source speed (100ms frames); English; text output.
  • settings: Same transcription-only instructions, VAD disabled, provider-default reasoning, no vocabulary hints / corrections / references.
  • reps: Three repetitions per model; six models × 6 attempts (two auth routes × 3).
  • auth: Both auth routes attempted SEPARATELY: ephemeral minted key vs direct AAD. 26 of 36 attempts were setup failures (timeouts / HTTP 408, including mint + WS).
  • scoring: Targeted diagnostics (Frank continuity, three-voices-distinct, latency), NOT WER/DER. No whole-meeting winner.
  • latency caveat: 'First text after commit' includes deliberate 15s accumulation; it is NOT minimum model latency.
  • base outlier: gpt-realtime median 0.597s but range reaches 18.597s — the outlier MUST stay visible; do not rank on median alone.
  • confound: Earlier 2.1 runs were on Caldova; others on temporary PAYG deployments. Both East US 2, but the account difference is a timing confound.
  • earlier pilot: An earlier 2.1 initial-pilot success is NOT included in this 36-attempt aggregate.
  • shortlist: 1.5 and 2.1 are TENTATIVE shortlist candidates only — full-meeting validation pending.

Sources: rubric and summary JSON under docs/benchmarks/2026-10-14-realtime-pilot/. Shortlist (1.5, 2.1) is tentative; full-meeting validation pending.

MAI batch & the cross-request label problem

Azure MAI-Transcribe-2 and the classic continuous path, from saved evidence. The core finding: streamed/chunked requests reset speaker IDs every call, so the same person is relabeled across chunks.

  • Full file: 1695.79s audio → HTTP 200 in 20.636s · 92 phrases · 4486 words · 8 unique speaker IDs (8 unique IDs — NOT verified as 8 distinct people.)
  • Chunked excerpt (s270–450, 10s chunks): 26 lines, 535 words. Speaker IDs restart per request. Speaker 0 assigned to multiple distinct self-introductions and both sides of dialogue. No cross-chunk matching.
  • 15s vs 10s chunks: 15s chunks do NOT solve cross-request label reset.
  • Rich config: HTTP 200 with word timestamps + clean style + phrase-list hints + en-US; default is verbatim. maxSpeakers rejected (HTTP 400); confidence 0 returned, not usable.
  • Quality metrics: WER / DER = unknown — No human-checked transcript/speaker reference exists.
  • CLI bug: EOF drained only two buffered chunks; now all full chunks + tail drain (was 2 requests instead of 19); 99 passed, 1 existing LibreSSL warning.

Proposed solutions & defaults

Cross-request speaker persistence is unsolved here. These approaches are proposed, none implemented. User defaults were left unchanged.

Candidate approaches

  • Hybrid: Azure continuous diarization + MAI word timestamps proposed (not implemented)
    Use classic continuous diarization for speaker continuity, MAI for word-level timing.
  • Local diarization via voice embeddings (diart) proposed (not implemented)
    Local speaker embeddings to persist identity across requests. source
  • OpenAI known-speaker references proposed (not implemented)
    Up to 4 known voices, 2–10s each, attached per request. OpenAI direct is DOCUMENTED; the Azure path is UNVERIFIED. source
